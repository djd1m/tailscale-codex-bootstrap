# Однократная подготовка Amsterdam-хаба

Это инструкция администратору tailnet. Клиентский установщик её автоматически не выполняет. Файл `examples/tailnet-policy.fragment.json` содержит демонстрационные адреса, а не готовую политику. Не заменяйте им действующую конфигурацию tailnet.

## Сначала выберите вариант размещения

| Ситуация | Порядок действий |
| --- | --- |
| На хабе уже работают сервисы и основной пользовательский Tailscale | **Рекомендуется отдельный Connector в Docker:** сначала следуйте [ISOLATED-CONNECTOR](ISOLATED-CONNECTOR.md). У него свои identity, Tailscale IP, state и socket. Основной host daemon не тегируют и не включают на нём роль Connector |
| Есть выделенная нода, идентичность и роль которой разрешено изменить | Допустим host-mode: команды `hub-check` и `sudo tailscale set` ниже относятся именно к её основному daemon |

Разделы policy и клиентской приёмки общие для обоих вариантов. **Команды host-mode не выполняются на основном daemon рабочего хаба ради контейнерного Connector.** Установщик клиента `bin/bootstrap` не устанавливает шлюз на хабе; Docker/Compose, TUN и независимые DNS в контейнерном варианте проверяет администратор по отдельному runbook.

## Сначала обследование

Репозиторий не содержит рабочую конфигурацию нашего хаба. `100.64.0.10` и `tail000000.ts.net` в примерах — условные значения. Согласованные Tailscale IP, MagicDNS suffix, тег и проверенный публичный egress задаются в локальном профиле вне Git.

Сначала отдельно проверьте версии Tailscale, текущие теги и роль App Connector, IPv4/IPv6 forwarding, firewall и владельца устройства. **Только для host-mode:** для локальной проверки роли на выбранной выделенной ноде передайте подготовленный профиль:

```bash
sudo env PYTHONPATH="$PWD/src" python3 -m tailnet_bootstrap.cli --profile /root/approved-egress-profile.json hub-check
```

`HUB_ROLE_PRESENT_POLICY_NOT_VERIFIED` подтверждает лишь ожидаемые локальный адрес, тег и включённую роль. Работоспособность проверяют с отдельного клиента. Отсутствие роли возвращает `NEEDS_HUB_ADMIN`; это не команда её включения.

В Docker-варианте `hub-check` через обычный host socket проверяет основной daemon, а не контейнер. Не исправляйте его ожидаемый `NEEDS_HUB_ADMIN` тегированием основного хаба. Проверки контейнерного daemon и его socket выполняются по [ISOLATED-CONNECTOR](ISOLATED-CONNECTOR.md).

## Перед изменением идентичности хаба

App Connector требует тега. При переводе пользовательского устройства в tagged device оно теряет пользовательскую идентичность; прежние разрешения могут измениться. Сначала:

1. Проверьте независимые SSH-ключи владельца, действующий OpenSSH и консоль провайдера. Оставьте управляющее соединение открытым.
2. Сохраните действующую политику tailnet и список назначенных тегов/маршрутов вне Git. Проверьте разрешения SSH, Mattermost, резервного копирования, телеметрии и связи с существующими нодами после перевода на тег.
3. Согласуйте конкретное изменение существующего хаба. Этот репозиторий не является разрешением на такое изменение.
4. Если перевод идентичности неприемлем, используйте отдельное tagged-устройство в Amsterdam. Есть [шаблон изолированного Docker connector](ISOLATED-CONNECTOR.md) на том же сервере. Укажите его собственный согласованный Tailscale IP и проверенный внешний egress в отдельном профиле. Существующий пользовательский хаб при этом менять не требуется. Создание Docker bridge всё равно меняет правила сети хоста, поэтому выполните предусмотренные проверки до и после запуска.

Не используйте `tailscale up --reset`. Не включайте Tailscale SSH, exit node или дополнительные SSH-forwarding разрешения ради этого пилота.

## Политика минимального пилота

До добавления новой VM проверьте всю действующую политику по [модели безопасности](SECURITY.md). Разрешение вида `src: ["*"], dst: ["*"], ip: ["*"]` сохраняет широкую связность, даже если рядом добавлен узкий grant для HTTPS через Connector. Другой root на клиентской VM контролирует эту сетевую идентичность и локальную авторизацию Codex. Изоляция контейнера Connector не заменяет разграничение доступа между узлами.

Администратор с правами Owner/Admin/Network admin объединяет фрагмент с действующей политикой и проверяет результат встроенным валидатором Tailscale:

1. Назначает **выбранной connector-ноде** `tag:ai-egress-hub`, пилотной VM — `tag:codex-pilot`. В Docker-варианте тег получает отдельная контейнерная identity, а не основной хаб. Пустые `tagOwners` оставляют назначение администратору; их можно заменить существующей группой администраторов.
2. Сначала настраивает один контролируемый HTTPS FQDN, возвращающий IP клиента, и его проверенные публичные A-адреса. `probe.example.com` и `192.0.2.42/32` необходимо заменить. В рабочем профиле используется `api.ipify.org`; у него нужно проверить все актуальные адреса.
3. Разрешает PeerAPI discovery клиента к connector через `tcp:53` и `udp:53`, а HTTPS — только к выбранным адресам через нужный connector (`via`). Разрешения складываются с уже существующими ACL/grants: узкий фрагмент не отменяет широкие разрешения.
4. Для стабильных адресов документированный `app.routes` позволяет предварительно задать маршруты. Для маршрутов, изученных через DNS, настраивает `autoApprovers.routes` только на проверенные конкретные префиксы и connector tag либо подтверждает конкретные маршруты вручную. `0.0.0.0/0` и `::/0` для автоматического одобрения не использовать.
5. Добавляет согласованный инвентарь FQDN авторизации и запросов установленного Codex. Стартовый список в примере не считается полным. CNAME/CDN, новые адреса и новые версии клиента требуют повторной проверки.

`nodeAttrs.target: ["*"]` в демонстрационном фрагменте распространяет конфигурацию приложения. Доступ к данным ограничивают grants всей эффективной политики; сам target не является ограничением доступа.

Для VM с другим root можно отдельно выбрать [необязательный режим изоляции](OPTIONAL-ISOLATION.md): собственная ограниченная tag identity, только discovery/HTTPS через Connector и отсутствие разрешений в обе стороны с остальными peers. Он не включается обычным bootstrap и требует проверки всей policy.

**Только для host-mode:** после назначения и проверки тега администратор включает существующую роль на выбранной выделенной ноде без сброса других параметров:

```bash
sudo tailscale set --advertise-connector=true
```

В Docker-варианте эту настройку выполняют внутри нового сервиса через его socket; команды приведены в [ISOLATED-CONNECTOR](ISOLATED-CONNECTOR.md). Основной host daemon сохраняет прежнюю роль.

Проверьте действующее IPv4 forwarding, правила FORWARD, штатный SNAT Tailscale и исходящий HTTPS. Автоматически сбрасывать iptables/nftables или менять правила Docker нельзя. Для начального IPv4-пилота VM должна не иметь пригодного исходящего IPv6; иначе приёмка блокируется до отдельного IPv6-проекта.

## Измерение адреса и приёмка

Измеряйте адрес из того сетевого namespace, который действительно пересылает трафик. Для Docker-варианта используйте namespace Connector и DNS/pinned-IP проверки из [ISOLATED-CONNECTOR](ISOLATED-CONNECTOR.md); один запрос с хоста не подтверждает egress контейнера.

**Только для host-mode:** на выбранной ноде измерьте настоящий публичный IPv4, не выводя секретов:

```bash
curl --disable --fail --silent --show-error --ipv4 --noproxy '*' --proto '=https' --connect-timeout 5 --max-time 15 https://api.ipify.org
```

Передайте это несекретное значение в клиентский профиль как `expected_egress_ipv4`. По одному Tailscale IP внешний IP определить нельзя.

С пилотной VM выполните `apply`, затем `verify` по инструкции. Приёмка: все текущие A-адреса выбранных доменов имеют маршрут `tailscale0`, соответствующие PrimaryRoutes выбирают нужный хаб, контрольный HTTPS возвращает измеренный IPv4 хаба, а независимый non-AI endpoint выходит обычным интерфейсом VM. Пригодный IPv6, посторонние маршруты и proxy-переменные блокируют проверку.

После реального входа и запроса Codex проверьте OAuth, refresh, inference и streaming, а также обычный неприкреплённый к IP HTTPS-запрос с системным DNS. Не записывайте токены или тело приватного запроса в отчёт. Проверка контрольного endpoint не доказывает, какой IP зафиксировал OpenAI.

## Откат центральной части

Сначала остановите пилотное использование и восстановите клиентский `accept-routes` командой `rollback`. Снимите только добавленные для пилота app/grants/одобрения, сверяя сохранённую политику. В host-mode роль connector можно выключить `sudo tailscale set --advertise-connector=false`, если она включалась только для пилота. В Docker-варианте используйте откат только нового сервиса по [ISOLATED-CONNECTOR](ISOLATED-CONNECTOR.md), основной daemon не меняйте. Возврат пользовательской идентичности устройства выполняйте по согласованному администратором плану: простое удаление тега не обещает восстановить прежний вход и права. При включённой изоляции не возвращайте широкий доступ автоматически: [порядок безопасного отката](OPTIONAL-ISOLATION.md#откат-и-завершение-допуска).
