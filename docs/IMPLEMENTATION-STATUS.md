# Состояние версии 0.1.0

Дата проверки: 25 ноября 2026 года.

## Готово

- Диалоговый launcher, отдельная tmux-сессия с прокруткой и продолжение по сохранённому состоянию.
- Проверка платформы; установка отсутствующих зависимостей, Tailscale и закреплённого полного пакета Codex.
- Настраиваемый локальный профиль: хаб, tailnet, тег, домены и проверенный внешний IPv4. Рабочие профили отсутствуют в Git.
- Защита хаба по ожидаемому адресу до клиентских изменений, включая раннюю установку tmux на уже подключённой машине; параметры `--profile` и `--state-dir` учитываются той же CLI.
- Аудит предлагаемых маршрутов, DNS, proxy/TLS-переопределений и IPv6 до включения `accept-routes`; сохранение baseline и контролируемый откат.
- Проверка всех текущих IPv4-ответов, выбранного connector и независимого HTTPS egress; отдельный non-AI контроль.
- Русские инструкции для человека, самостоятельного ИИ и пошагового ИИ с критериями приёмки.
- HLD/LLD, Mermaid packet flow, центральная инструкция и независимое ревью.

## Проверки реализации

`make check`: 90 тестов прошли; Python компилируется, синтаксис Bash launcher проверен. Тесты используют подставные ответы для Tailscale/apt/маршрутизации; они не меняют действующие службы. Отдельно проверены ссылки документации, синтаксис её Bash-примеров и сборка wheel с включённым `installer-lock.json`.

Проверены сценарии несовпадения tailnet, постороннего маршрута, неправильного connector, доступного/предлагаемого IPv6, неверного внешнего IP, изменения настроек во время apply, аварии после применения, повторного запуска, частичной установки Codex, подмены checksum, конкурирующих процессов, переполнения вывода и тайм-аута.

## Ещё не подтверждено

- Чистая установка на реальной Cloud.ru VM для каждой пары ОС/архитектуры.
- Готовность конкретного App Connector и эффективной политики tailnet.
- Живой маршрут Cloud.ru → согласованный хаб → провайдер.
- Собственный OAuth-вход, реальный ответ Codex, refresh и streaming через этот маршрут.
- Поведение после reboot реальной VM и повторная живая приёмка после изменения DNS.

Статус версии — **реализация для контролируемого пилота**, а не завершённый сетевой пилот. Результат `NETWORK_VERIFIED` является снимком проверки; автоматического `CODEX_VERIFIED` нет. Не обещается постоянная блокировка прямого обходного выхода.

## Следующий шаг

Администратор подготавливает центральную часть по `HUB-SETUP.md`, владелец предоставляет чистую VM и проверенные параметры. Затем оператор проходит `ACCEPTANCE.md` и пошаговый runbook, фиксируя фактические результаты и ограничения. Пока центральная часть не готова, клиент должен останавливаться с блокерами.
