# Runbook для самостоятельного AI

Работай на целевой новой VM, сохраняя доступ пользователя и существующую конфигурацию. Задача: установить нативный Codex, подключить VM к согласованному tailnet, проверить IPv4 HTTPS к выбранным доменам через существующий App Connector. Выполни доступную часть; при реальном административном или авторизационном блокере выдай точное действие для владельца и текущий статус.

Прочитай [README](../README.md), [приёмку](../docs/ACCEPTANCE.md) и [диагностику](../docs/TROUBLESHOOTING.md). До изменения согласованного Amsterdam-хаба нужна отдельная авторизация. Проверь его готовность с администратором; примеры в публичном коде не являются наблюдениями рабочего развёртывания.

## Контракт

- Платформы: Ubuntu 22.04/24.04, Debian 12/13, amd64/arm64, systemd. При другом варианте остановись без подмены `/etc/os-release`.
- `configure` запрашивает Tailscale IPv4 hub из `100.64.0.0/10`, MagicDNS suffix tailnet и connector tag; профиль v1 фиксирует согласованные параметры конкретной установки. `100.64.0.10`, `tail000000.ts.net`, `tag:ai-egress-hub` — примеры, не рабочие значения. Домены точные, без wildcard; состав для реального Codex требует наблюдений. `api.ipify.org` входит в `domains`, `checkip.amazonaws.com` — вне списка. Ожидаемый внешний IPv4 hub должен быть подтверждён, не угадан.
- Нельзя менять SSH, firewall, exit node, прокси, теги, remote hub, перезагружать VM или обходить проверки. Изменение маршрутизации клиента — только согласованный `accept-routes=true` после аудита и baseline.
- Не запрашивай и не копируй auth keys, токены, пароли и чужие данные Codex. Собственный пользовательский device auth завершается человеком. Не отправляй коды/URL входа в отчёты.
- Код публичный: `git clone` не требует аккаунта GitHub, токена или авторизации. Если GitHub недоступен, используй проверенный несекретный архив исходников. Не публикуй рабочие профили, state и сведения конкретного развёртывания.

## Выполнение

1. Read-only: проверь ОС, архитектуру, PID 1, наличие `sudo`, доступ к репозиторию. Согласуй профиль с администратором; не заменяй неизвестный публичный IP примером.
2. Из корня репозитория запусти `sudo bash bin/bootstrap`. Для отсутствующих `python3`/`tmux` launcher получает подтверждение отдельно. Сессия: socket `ai-egress-bootstrap`, имя `node-bootstrap`, mouse on, history 100000. Wizard создаёт профиль первым шагом; `install`/`connect` требуют готовый профиль. Если локальный Tailscale IP совпадает с `hub_ip` профиля, остановись: клиентскую установку нельзя выполнять на hub.
3. Пройди `configure` и `install`. Рабочий профиль по умолчанию `/var/lib/tailscale-codex-bootstrap/profile.json`; `profiles/pilot.example.json` — шаблон с намеренно нерабочим `203.0.113.10`. Новая установка — официальный полный пакет Codex 0.172.0; существующий рабочий CLI не заменяется и может иметь `package_verified: false`. Версии и комплектность проверяй отдельно. Wizard работает от root: новый Codex устанавливается в `/root/.local/bin`, использует root home, авторизация пользователя SSH не переносится. Не добавляй флаги обхода разрешений Codex.
4. `connect`: разрешён только новый отключённый Tailscale-узел без существующей идентичности, с подтверждением и браузерным входом владельца. При существующем узле/другом tailnet остановись для согласованного решения; не делай logout, reset или forced reauth.
5. `apply`: без готового уникального hub с нужным тегом и одобренными маршрутами не объявляй сеть готовой. Аудит должен исключить неожиданные предлагаемые маршруты и exit node. `accept-routes` разрешает маршруты tailnet в целом, поэтому не игнорируй этот аудит. Сохрани baseline и получи явное подтверждение предусмотренным интерактивным шагом. `hub-check` проверяет локальную роль **на самом hub**, а не удалённый hub с новой VM.
6. `verify`: требуй `NETWORK_VERIFIED`, пустой список блокеров и фактические evidence. Проверь текущие DNS, точные `/32` PrimaryRoutes у нужного hub, `tailscale0`, независимый echo с ожидаемым IPv4 и контроль прямого не-AI выхода. IPv6 с возможным выходом требует отдельной приёмки, не отключай его молча.
7. Мастер заканчивается после сетевой приёмки. Затем отдельно — `login`, собственный `codex login --device-auth`, `launch`. Для ручной отметки `CODEX_VERIFIED` необходим успешный реальный запрос и наблюдаемое покрытие OAuth/inference/streaming endpoint-ов. `--version`, успешный login и unit-тесты этого не доказывают. CLI не присваивает `CODEX_VERIFIED`: `verify` оставляет `codex_acceptance=NOT_TESTED`, login/launch — `MANUAL_VERIFICATION_REQUIRED`.
8. Запиши итог по матрице. Если ручной пилот не выполнен, прямо укажи «Codex live pilot не выполнен», даже при `NETWORK_VERIFIED`.

В root-shell tmux:

```bash
PYTHONPATH=src python3 -m tailnet_bootstrap.cli status
PYTHONPATH=src python3 -m tailnet_bootstrap.cli verify
PYTHONPATH=src python3 -m tailnet_bootstrap.cli rollback
```

В обычном shell из корня репозитория:

```bash
sudo env PYTHONPATH="$PWD/src" python3 -m tailnet_bootstrap.cli --profile /absolute/path/profile.json verify
```

Глобальные флаги `--profile`/`--state-dir` идут перед подкомандой. Не используй несуществующий `--yes`. `hub-check` — диагностика роли локального hub, не удалённая настройка; его указания ведут в [HUB-SETUP](../docs/HUB-SETUP.md).

## Восстановление

При разрыве SSH: `sudo tmux -L ai-egress-bootstrap attach -t node-bootstrap`. При наличии сессии повторный launcher игнорирует новые аргументы и только подключается. После reboot заново выполни `sudo bash bin/bootstrap`: state продолжит этапы, процесс и история tmux не восстановятся.

Default state `/var/lib/tailscale-codex-bootstrap`, каталог `0700`, файлы `0600`; не помещай туда секреты. Не удаляй state при ошибке: в нём baseline отката. `rollback` меняет только исходное `accept-routes` с проверкой идентичности и текущего значения, не является удалением установки.

Не называй App Connector фильтром для процесса Codex: маршруты действуют по IP для всех процессов; общий CDN затрагивает другие hostnames. Удаление маршрута и новые DNS-ответы могут дать прямой выход. V1 не fail-closed, независимый echo не измеряет IP на стороне OpenAI, а автоматические тесты не являются живой приёмкой инфраструктуры.

Итог: отдельно `installed` + сведения о package verification, `NETWORK_VERIFIED`/точные блокеры, `CODEX_VERIFIED`/невыполненный пилот, команды доказательств и время наблюдений. Не делай выводов о будущих DNS-ответах по разовому снимку.
