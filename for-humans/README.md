# Инструкция оператору

Цель — подготовить новую VM и проверить выбранные HTTPS-направления через согласованный Amsterdam-хаб. Сначала установка программ, затем сеть, затем собственный вход и реальный запрос Codex. Это три разные приёмки.

## Перед началом

Подходит Ubuntu 22.04/24.04 или Debian 12/13 с systemd на amd64/arm64. У вас должны быть `sudo`, работающий SSH/консольный доступ, DNS и исходящий HTTPS. Дождитесь завершения первичной настройки Cloud.ru / cloud-init.

Если root на VM доступен другим людям, они могут пользоваться вашей локальной авторизацией Codex. Сначала согласуйте доверие к машине и разрешения tailnet по [инструкции безопасности](../docs/SECURITY.md). Рабочий App Connector и `NETWORK_VERIFIED` не подтверждают изоляцию от остальных узлов. Понятное объяснение схем и сценариев — в [путеводителе HLD/LLD](../docs/HLD-LLD.md).

Если VM нужна только на время настройки, сначала выберите [сценарий временного доступа](../docs/TEMPORARY-ACCESS.md). При настройке с хаба по SSH личный Codex на VM не требуется, и его OAuth туда не передаётся. У нынешнего мастера нет автоматического режима удаления временного допуска.

Администратор hub должен предоставить:

- проверенные Tailscale IPv4 hub, MagicDNS suffix tailnet, connector tag и подтверждение готовности App Connector; `100.64.0.10`, `tail000000.ts.net`, `tag:ai-egress-hub` в примерах не являются рабочими параметрами;
- утверждённый список **точных** доменов, включая `api.ipify.org` для независимой проверки;
- подтверждённый публичный IPv4 hub для `expected_egress_ipv4`;
- подтверждение необходимых policy/route approvals для вашей VM.

Готовность центральной части нужно проверить отдельно: тег, роль App Connector, policy и route approvals. Без этих подтверждений сеть не принята. Не пытайтесь компенсировать отсутствие настройки exit node, прокси или ручными статическими маршрутами. [Подготовка hub](../docs/HUB-SETUP.md).

## Получить исходники и запустить

Публичный репозиторий клонируется без GitHub-аккаунта, токена и авторизации. Если GitHub недоступен, попросите администратора передать проверенный архив исходников без рабочих профилей и секретов; затем распакуйте его. На VM не нужны чужие `.codex`, Tailscale state или auth keys.

Если исходники получаете через GitHub, но `git` отсутствует, сначала выполните `sudo apt-get update`, затем `sudo apt-get install --no-install-recommends git ca-certificates`. После этого используйте `git clone` из [README](../README.md). При apt lock сначала дождитесь cloud-init/другого apt, не удаляйте lock-файлы.

Из каталога репозитория:

```bash
sudo bash bin/bootstrap
```

Если отсутствуют `python3` и `tmux`, launcher спросит разрешение на их установку. После этого мастер работает в tmux. Подтверждайте только понятные вам действия: установка пакетов, вход нового узла в Tailscale и изменение `accept-routes` имеют отдельные шаги.

Укажите профиль в мастере либо передайте его при первом запуске:

```bash
sudo bash bin/bootstrap --profile /absolute/path/profile.json
```

В мастере укажите подтверждённые Tailscale IPv4 hub, tailnet suffix и connector tag. `expected_egress_ipv4` должен быть настоящим публичным адресом hub. В `profiles/pilot.example.json` все параметры демонстрационные, а внешний адрес `203.0.113.10` намеренно нерабочий: пример нельзя использовать без замены параметров согласованными значениями. Мастер по умолчанию сохраняет рабочий профиль в `/var/lib/tailscale-codex-bootstrap/profile.json`, вне Git. Не добавляйте `checkip.amazonaws.com` в `domains`: это контроль прямого выхода с VM.

## Пройти мастер

1. **Профиль и установка.** Сначала мастер создаёт профиль; отдельные `install` и `connect` тоже требуют готовый профиль. Он проверяет платформу и исключает запуск клиентской установки на hub по его IP из профиля, устанавливает недостающие пакеты и Tailscale, запускает daemon. При отсутствии Codex устанавливается закреплённый полный официальный пакет 0.172.0. Рабочий существующий CLI сохраняется, даже если его полный пакет не удалось подтвердить.
2. **Tailscale.** Для нового отключённого узла без существующей идентичности мастер предлагает `tailscale up` и браузерный вход. Войдите в нужный tailnet своей учётной записью. Существующий узел не заменяется. Не копируйте auth keys и не вставляйте их в команды.
3. **Маршруты.** Мастер сначала проверяет tailnet, настройки и предлагаемые маршруты. Неожиданные subnet routes, exit node или неготовый hub требуют разбирательства. Только после успешного аудита и вашего согласия включается `accept-routes`; исходное значение сохраняется.
4. **Сетевая проверка.** Нужен `NETWORK_VERIFIED` без блокеров. Проверяются точные маршруты текущих DNS-адресов через нужный hub, независимый IP echo и прямой выход контрольного не-AI домена. Это ещё не проверка Codex.
5. **Codex.** Мастер завершится после сетевой проверки. Отдельно запустите `login`, завершите `codex login --device-auth` своей учётной записью, затем `launch`. Выполните обычный реальный запрос и проверьте endpoint-ы клиента по [матрице приёмки](../docs/ACCEPTANCE.md). Только этот отдельный пилот позволяет записать ручную отметку `CODEX_VERIFIED` в итоговый отчёт. CLI её автоматически не выставляет: сетевой отчёт содержит `NOT_TESTED`, а результат login/launch — `MANUAL_VERIFICATION_REQUIRED`.

При запросе URL или кода авторизации используйте их сами в браузере. Не отправляйте коды, ссылки входа, `auth.json` и вывод с токенами в чат или issue. Авторизацию хранит сам Codex, bootstrap её не переносит.

Весь мастер работает от root. Новый Codex устанавливается в `/root/.local/bin`, его локальные данные относятся к root home. Это собственный вход владельца в этом окружении; авторизация пользователя SSH не копируется. Bootstrap не добавляет флаги обхода разрешений Codex.

## Если SSH оборвался

```bash
sudo tmux -L ai-egress-bootstrap attach -t node-bootstrap
```

Отсоединение: `Ctrl-b`, затем `d`. Колесо мыши прокручивает вывод; история — до 100 000 строк. tmux продолжает процесс после разрыва SSH, пока VM работает. После reboot запустите `sudo bash bin/bootstrap` заново: новая сессия прочитает сохранённые этапы. Процесс и история tmux после reboot не восстанавливаются.

Повторный `bin/bootstrap` при существующей сессии только подключает к ней; новые аргументы не выполняются. В shell внутри сессии можно выполнить:

```bash
PYTHONPATH=src python3 -m tailnet_bootstrap.cli status
PYTHONPATH=src python3 -m tailnet_bootstrap.cli verify
PYTHONPATH=src python3 -m tailnet_bootstrap.cli login
PYTHONPATH=src python3 -m tailnet_bootstrap.cli launch
```

Вне root-сессии используйте `sudo env PYTHONPATH="$PWD/src" python3 -m tailnet_bootstrap.cli status` из корня репозитория. Не запускайте одновременно несколько мастеров с разными state-каталогами.

## Откат и завершение

```bash
sudo env PYTHONPATH="$PWD/src" python3 -m tailnet_bootstrap.cli rollback
```

Откат касается только `accept-routes`, изменённого этим bootstrap. Он проверяет сохранённую идентичность и текущее значение, а при несовпадении останавливается. Не удаляет пакеты, аккаунт или узел, не меняет SSH/firewall и не трогает hub.

В конце сохраните короткий отчёт: VM/ОС, время, профиль, установленные версии и `package_verified`, результат `verify`, неразрешённые блокеры и отдельно результат ручного пилота Codex. Укажите `installed`, `NETWORK_VERIFIED` и `CODEX_VERIFIED` только в пределах реально выполненных проверок. Независимый IP echo не доказывает, какой IP увидел OpenAI.

Состояние лежит в `/var/lib/tailscale-codex-bootstrap` (`0700`, файлы `0600`); оно не должно содержать секреты, но раскрывает инфраструктуру. Полное содержимое не публикуйте. Разбор ошибок — в [TROUBLESHOOTING](../docs/TROUBLESHOOTING.md).
