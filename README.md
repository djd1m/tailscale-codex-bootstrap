# Tailscale → Codex: установщик для новой VM

Интерактивная подготовка Linux VM в Cloud.ru для **нативного Codex CLI** и HTTPS к выбранным доменам через согласованный Amsterdam-хаб в Tailscale. Интернет к остальным адресам должен выходить напрямую с VM. Это репозиторий для пилота; наличие установленных программ не подтверждает работу маршрутизации или Codex.

Поддерживаются Ubuntu 22.04/24.04 и Debian 12/13, `amd64`/`arm64`, systemd. Нужны доступ `sudo`, интерактивный терминал, исходящий HTTPS и DNS для получения пакетов и входа в Tailscale. Bootstrap не настраивает Cloud.ru, SSH или доступ к самой VM.

**Готовность hub проверяется отдельно администратором.** Публичный репозиторий не содержит параметры или результаты проверки какого-либо рабочего tailnet. Примеры `100.64.0.10`, `tail000000.ts.net` и `tag:ai-egress-hub` нужно заменить согласованными значениями. Установщик на новой VM не назначает hub тег, не меняет tailnet policy, не включает App Connector на удалённом узле и не подтверждает его внешний IP. Подготовка hub описана в [документации администратора](docs/HUB-SETUP.md). Для действующего хаба с пользовательской идентичностью предусмотрен [отдельный connector в Docker](docs/ISOLATED-CONNECTOR.md); его собственный Tailscale IP становится `hub_ip` клиентского профиля.

## Быстрый запуск

Исходный код опубликован в публичном репозитории. Для `git clone` не нужны аккаунт GitHub, токен или настроенная авторизация. Рабочие профили и локальное состояние остаются вне Git.

Если `git` ещё нет на новой VM, сначала установите его из штатного репозитория ОС:

```bash
sudo apt-get update
sudo apt-get install --no-install-recommends git ca-certificates
```

```bash
git clone https://github.com/djd1m/tailscale-codex-bootstrap.git
cd tailscale-codex-bootstrap
sudo bash bin/bootstrap
```

Если GitHub на свежей VM недоступен, администратор может передать проверенную копию исходников архивом с доступного hub. Архив должен содержать исходники репозитория, без `.git`, рабочих профилей, локального состояния, `.codex`, ключей и файлов авторизации. Распакуйте его, перейдите в каталог и выполните ту же команду `sudo bash bin/bootstrap`. Не передавайте авторизацию Codex или Tailscale с другого компьютера.

Launcher предложит установить `python3` и `tmux`, если их нет. Затем мастер продолжит работу в отдельной tmux-сессии. Он запросит подтверждения перед установкой, подключением нового узла к Tailscale и включением приёма маршрутов. Режима без вопросов и флага `--yes` нет.

Мастер ведёт по этапам:

1. Выбрать и проверить профиль с точными доменами и подтверждённым публичным IPv4 hub.
2. Установить недостающие пакеты, Tailscale из подписанного apt-репозитория и Codex.
3. Подключить новый узел к нужному tailnet через браузер пользователя.
4. Проверить готовность hub и все предлагаемые маршруты, сохранить исходные параметры и отдельно подтвердить `accept-routes`.
5. Выполнить сетевые проверки. Только успешный результат даёт `NETWORK_VERIFIED`.
6. После завершения мастера отдельно запустить `login` и `launch`: войти в **собственный** аккаунт Codex через device auth и выполнить реальный запрос для отдельной приёмки Codex.

Полная инструкция: [для человека](for-humans/README.md), [для самостоятельного AI](for-ai-smart/README.md), [пошаговая для AI с обязательными проверками](for-ai-dumb/README.md).

## Как устроено решение

Это выборочная IP-маршрутизация через Tailscale App Connector. В Codex не задаётся HTTP/SOCKS proxy; HTTPS остаётся сквозным между CLI и OpenAI.

| Что хочется понять | Где читать |
| --- | --- |
| С чего начать и в каком порядке читать схемы | [Путеводитель по архитектуре](docs/HLD-LLD.md) |
| Компоненты, границы доверия, управляющий и рабочий трафик | [HLD — анатомия решения](docs/HLD.md) |
| Интерфейсы, DNS, таблицы маршрутов, два SNAT и состояние | [LLD — устройство соединения](docs/LLD.md) |
| Вход, запрос и streaming, прямой интернет, DERP и отказы | [Packet walk по сценариям](docs/PACKET-FLOW.md) |
| Второй root, доступ к другим узлам, авторизация Codex и отключение VM | [Безопасность и отзыв доступа](docs/SECURITY.md) |
| Быстро подключить VM для настройки и затем завершить временный допуск | [Временный доступ и очистка](docs/TEMPORARY-ACCESS.md) |
| Чем доказать результат | [Матрица приёмки](docs/ACCEPTANCE.md) и [независимое ревью](docs/INDEPENDENT-REVIEW.md) |

**До входа в личный Codex оцените доверие к VM.** Другой root на ней может получить локальную авторизацию и использовать её. Членство в tailnet и App Connector сами по себе не изолируют VM от остальных узлов: это должна обеспечивать вся действующая политика доступа. Сетевая проверка `NETWORK_VERIFIED` не является проверкой такой изоляции.

## Профиль

Мастер `configure` запрашивает Tailscale IPv4 hub, MagicDNS suffix tailnet, connector tag, публичный IPv4 выхода и список доменов. Профиль v1 фиксирует выбранные значения для этой установки; они не зашиты в код. Значения в таблице — примеры:

| Поле | Значение / требование |
| --- | --- |
| `version` | `1` |
| `hub_ip` | Проверенный Tailscale IPv4 hub из `100.64.0.0/10`, например `100.64.0.10` |
| `expected_tailnet` | Подтверждённый MagicDNS suffix, например `tail000000.ts.net` |
| `connector_tag` | Согласованный тег App Connector, например `tag:ai-egress-hub` |
| `domains` | Точные lowercase FQDN, без `*`, схемы, порта и завершающей точки |
| `expected_egress_ipv4` | Реальный публичный IPv4 hub, проверенный администратором |
| `probe_domain` | `api.ipify.org`, обязательно включён в `domains` |
| `probe_url` | `https://api.ipify.org` |
| `non_ai_probe_url` | `https://checkip.amazonaws.com`, домен вне `domains` |

Нельзя подставлять Tailscale IP hub в `expected_egress_ipv4`. Адрес Cloud.ru VM также не подходит. [Пример профиля](profiles/pilot.example.json) содержит демонстрационные hub/tailnet/tag и намеренно нерабочий внешний `203.0.113.10`, который не пройдёт проверку публичного адреса. Не используйте пример как рабочий профиль: подтвердите все параметры с владельцем и создайте локальный профиль мастером вне Git; по умолчанию это `/var/lib/tailscale-codex-bootstrap/profile.json`. Наличие примера не означает, что домены уже объявлены на hub и маршруты одобрены. Состав доменов для OAuth, inference и streaming должен подтверждаться наблюдением реального клиента. Добавление домена в локальный JSON само по себе не меняет App Connector.

## Что меняет bootstrap

После настройки профиля и отдельных подтверждений он устанавливает недостающие пакеты, добавляет проверенные ключ и apt source Tailscale, запускает `tailscaled.service`, устанавливает Codex и при необходимости подключает новый Tailscale-узел. `install` и `connect` требуют настроенный профиль; wizard создаёт его первым шагом. Клиентскую установку нельзя выполнять на узле, чей локальный Tailscale IP совпадает с `hub_ip` профиля. Для маршрутизации меняется только настройка клиента `tailscale set --accept-routes=true`, после аудита и сохранения исходного значения. Уже настроенная идентичность Tailscale не заменяется.

Новая установка Codex использует закреплённый официальный **полный пакет 0.172.0** с проверкой загрузчика и наличия компонентов. Уже работающий Codex сохраняется; успешные `--version` и `--help` не обязательно означают `package_verified: true` для существующей установки.

Launcher и мастер работают от root. Новый Codex устанавливается в `/root/.local/bin` и использует root home для своих локальных данных; вход в аккаунт всё равно выполняет владелец лично. Bootstrap не копирует авторизацию пользователя SSH и не добавляет флаги обхода разрешений или sandbox Codex.

Bootstrap не изменяет SSH, firewall, exit node, proxy-настройки, теги и конфигурацию hub, не перезагружает VM. `rollback` восстанавливает только сохранённое значение `accept-routes`, если идентичность узла и текущее значение позволяют безопасно сопоставить изменение. Он не удаляет программы, узел из tailnet или авторизацию Codex.

## Переподключение и состояние

После разрыва SSH:

```bash
sudo tmux -L ai-egress-bootstrap attach -t node-bootstrap
```

`Ctrl-b`, затем `d` отсоединяет терминал от сессии. Прокрутка мышью включена; история ограничена 100 000 строк. Для режима копирования: `Ctrl-b`, затем `[`, выход — `q`. tmux сохраняет процессы при разрыве SSH, пока работает VM. **Перезагрузка уничтожает процесс, сессию и её историю**; снова запустите `sudo bash bin/bootstrap`, чтобы создать сессию и продолжить по сохранённым этапам.

Если сессия уже существует, `bin/bootstrap` подключает к ней и **не запускает новые аргументы**. Для отдельной команды используйте shell внутри сессии или сначала завершите прежнюю сессию после остановки её работы.

Служебные данные по умолчанию находятся в `/var/lib/tailscale-codex-bootstrap`: каталог `0700`, файлы `0600`. Там хранятся профиль, этапы, сетевые доказательства и исходные настройки; не auth keys, пароли или токены. Авторизацией управляют штатные Tailscale и Codex. Не публикуйте весь state: он содержит адреса и сведения об инфраструктуре.

## Отдельные команды

Из корня репозитория, в shell tmux-сессии:

```bash
PYTHONPATH=src python3 -m tailnet_bootstrap.cli status
PYTHONPATH=src python3 -m tailnet_bootstrap.cli verify
PYTHONPATH=src python3 -m tailnet_bootstrap.cli rollback
```

При запуске вне root-сессии добавьте `sudo env PYTHONPATH="$PWD/src"` перед `python3`. Глобальные параметры указываются **до** подкоманды:

```bash
sudo env PYTHONPATH="$PWD/src" python3 -m tailnet_bootstrap.cli --profile /absolute/path/profile.json verify
```

Доступны `wizard` (по умолчанию), `configure`, `install`, `connect`, `apply`, `verify`, `status`, `rollback`, `login`, `launch`, `hub-check`; глобально — `--profile PATH` и `--state-dir PATH`. Используйте один каталог состояния для одной VM и одного профиля. `status` показывает сохранённый прогресс; свежую готовность определяет `verify`. `hub-check` предназначен для запуска **на самом hub**: проверяет его локальную роль, не подтверждает policy и не исправляет удалённый узел. Его запуск на новой VM не проверяет согласованный Amsterdam-хаб.

## Что считается результатом

| Статус | Что доказано |
| --- | --- |
| `installed` — отметка оператора | Программы установлены или обнаружены; отдельная отметка показывает проверку полного пакета Codex. Сеть и вход в Codex этим не проверены. |
| `NEEDS_HUB_ADMIN` | Нужны действия администратора hub/tailnet; локальную установку можно сохранить, сетевую готовность объявлять нельзя. |
| `NETWORK_NOT_VERIFIED` | Есть сетевые блокеры или не хватает наблюдений. |
| `NETWORK_VERIFIED` | Текущий IPv4-снимок DNS/маршрутов и независимых HTTPS-контролей прошёл проверки. |
| `CODEX_VERIFIED` — ручная отметка | Собственный вход, успешный реальный запрос Codex и наблюдаемое покрытие его endpoint-ов маршрутизацией. CLI не присваивает этот статус автоматически. |

Сетевой отчёт `verify` содержит `codex_acceptance: NOT_TESTED`. После `login`/`launch` сохраняется `MANUAL_VERIFICATION_REQUIRED`, даже если процесс завершился успешно.

Ответ `api.ipify.org` показывает IP, который увидел **этот независимый endpoint**. Он не показывает IP, увиденный OpenAI. Автотесты репозитория не являются живым тестом Cloud.ru, hub, tailnet, OAuth или inference. Полная [матрица приёмки](docs/ACCEPTANCE.md) отделяет эти проверки.

## Границы маршрутизации

Tailscale App Connector даёт маршруты **к IP-адресам**, найденным через DNS. Ими пользуются все процессы VM. Общий CDN/IP может отправить через hub и другой домен; это не фильтрация только процесса Codex или HTTP Host.

V1 проверяет текущие IPv4-ответы и конкретный hub. Доступный IPv6-путь блокирует такую приёмку и требует отдельного решения администратора. DoH, будущие DNS-ответы, UDP/443, дополнительные OAuth/inference/streaming endpoint-ы и альтернативные настройки клиента требуют отдельной проверки.

Это **не строгий fail-closed**: при исчезновении маршрута App Connector или появлении нового DNS-адреса трафик может пойти напрямую. Не считайте кратковременное `NETWORK_VERIFIED` постоянной гарантией. Для запрета прямого выхода требуется отдельная архитектура и приёмка; bootstrap такой firewall не создаёт.

При ошибке используйте [диагностику](docs/TROUBLESHOOTING.md), сохраните несекретные доказательства и остановитесь на первом неразрешённом блокере.
